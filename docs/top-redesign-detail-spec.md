## 2. レイアウト契約 TOP-01・02

### 2.1 DOMと縦スクロール

採用する論理構造は次の通り。実装時のクラス名は既存との整合を保つ。PC/SPで同じマップ・カードを使い、二重DOMと別々の取得処理を作らない。

```text
header.site-header
main#top.site-page
  マップ領域（PC sticky、SP通常フロー）
    .map-stage（背景＋装飾＋a.map-card > img）
  情報領域（通常フロー）
    h1#hero-title と紹介
    マップ操作案内（PCは犬タロー上半身＋吹き出し）
    7 section（既存IDを維持）
    フッターの内容
```

SPはサイト見出しをマップより前へ配置する。実装では単一のH1と紹介をCSS gridの領域配置で切り替え、読み上げ順が「サイト紹介→マップ→おすすめ」となるDOMを使う。上記は領域の説明であり、H1をマップ後に固定するDOM順の指定ではない。必要ならサイト紹介を共通gridの独立子にし、PCだけ右上へ配置する。

PCでもdocumentを縦スクロールの主体にする。右領域に固定高＋overflow-y:autoを設けない。地図はヘッダー下でstickyにし、7枠と右フッターまでstickyが成立する親領域を確保する。祖先overflowによってstickyが止まる現行SP `.site-page { overflow:hidden }` をそのまま持ち込まない。横方向のクリップはカルーセルトラックなど必要箇所へ限定する。

### 2.3 可変画面の計算

```text
Hmap = 表示高 − ヘッダー実測高 − 上24 − 下24
Wmap = Hmap × R（同じマップ枠の比率）
Wleft = 左余白 + Wmap + 右余白
Wright = 表示幅 − Wleft
```

Figma枠の基準Rは490.7/780。素材座標は第3節で別に管理し、背景の502×799とは区別する。中間画面でも素材と背景を同じ座標変換に含める。

右領域の必要幅はカードだけでなく、全6枠の「見出し＋すべて見る」が同じ行に収まる幅で決める。左右余白を各120から各24まで減らし、それでも必要幅を確保できなければ縦積みにする。PCで一覧リンクを無理に見出しへ重ねたり、文字やマップを一括縮小して2列を維持したりしない。

```text
WcardMin = 24×2 + 321 + 22 + 次カード見切れ23 = 414
WheadingMin = 24×2 + max(見出し外寸 + 行内gap16 + 一覧リンク実幅 + 右影4)
WrightMin = max(WcardMin, ceil(WheadingMin))
```

見出し外寸には文字、小丸、要素間12、左右padding21、左右border3を含める。一覧リンクも実装でpadding等を付ける場合はその外寸を使う。2.1の局所試作では既存JPフォント29pxの「キャラクター紹介」が外寸297.81px、一覧15pxが71.66pxで、WheadingMinは切り上げ438px。414pxでは行内容が19.47pxはみ出し、440pxでは収まった。このため通常書体での初期候補は440pxとし、414pxだけで切り替える案は採用しない。

440pxは新TOP全体の検証済み閾値ではない。全見出し・フォント読込前後/失敗・200%拡大・境界前後で必要幅を再確認し、より広ければ実測値を優先する。特に幅1024・高さ1366のような条件を確認し、採用閾値をG06で固定する。縦積み時はSPと同じ見出し下・右寄せの一覧配置へ切り替える。320pxや文字拡大でカプセル自体が収まらない場合は幅を親以内に制限してテキストを折り返し、見出し行・セクションを高くする。文字のクリップや書体変更で解決しない。

| PC viewport | サイト見出し | 案内 | ニュース | ニュース下端／余白 |
| --- | ---: | ---: | ---: | --- |
| 1440×900 | 92 | 168 | 544 | 876／24 |
| 1366×768 | 72 | 56 | 544 | 744／24 |
| 1280×720 | 56 | 52 | 516 | 696／24 |

案内使用可能高＝表示高−ヘッダー実測高−サイト見出し実測高−ニュース実測高−24。900px高では犬タロー枠130×136、吹き出し高112、本文22/30。低い画面では案内を短縮するが、最小52でも文が収まらなければ通常フローで伸ばす。200%拡大時はニュースの一画面表示より可読性を優先する。OSの画面解像度ではなくブラウザのコンテンツ領域で判定する。

## 3. マップ画像・遷移契約 TOP-03〜05

### 3.1 共通素材と座標

Figmaは背景の画像フィル＋16枚の「個別素材 / 素材名」。各画像に直接Click反応を設定済みで、透明な操作用フレームは撤去済み。位置調整はその画像レイヤーを選び、DesignのX/Y/W/Hで行う。PrototypeのClickから行き先を変更できる。本文・カード・地図全体を1枚の画像へ統合しない。

| --- | --- | --- |
| 地面・道路 | map_bg.svg | 背景のみ |
| 上左の建物 | map_illast.svg | イラスト |
| ゲーム | map_game.svg | 1 |
| ブログ | map_note.svg | 1 |
| キャラクター紹介 | map_character.svg | 1 |

| YouTube | map_youtube_bg.svg、map_youtube.svg、動画画像 | Webは背景→サムネイル/統計→看板の3層を1リンクに内包。Figmaの2画像は静的見本 |
| 木 | map_decoration_tree.png | 4 |
| さすけ・ぶくろちゃん・鳥 | map_decoration_sasuke.png、map_decoration_bukurochan.png、map_decoration_bird.png | 各1 |

上記は原本との対応。配信用には既存manifestが対応付けるWebP等を優先し、拡大後の必要解像度を満たすものはそのまま使う。不足する画像だけ第3.4節で再選定する。表示用画像の書き出しし直しは字形・色・透過・viewBoxと性能の回帰確認が必要。

旧画像組立の基準は `drafts/top-existing-assets-20261015/render.cjs` の502×799。最終座標は同期したFigma本体から抽出し、素材キー、x/y/w/h、重なり順を単一の定義で管理する。PC/SP別々の座標をCSSへ記述しない。座標は画像レイヤーの外接矩形であり、絵の不透明部分だけの境界ではない。元画像比率を維持し、枠比率差は背景と素材をまとめてcontain変換する。

保存済み取得値は `drafts/top-redesign-sdd-20261018/figma-current.json`。2026-10-18に利用者がPC本体基準を選択し、直接UIでPCのx132.5/y437・245.03角を再確認。SPをx92.3501/y304.5657・170.78角へ同期した。WebはPC490.7×780に対する共通の比率を採用する。旧透明ヒット領域の6点の%表は廃止する。補助操作見本の同期とは区別する。

### 3.2 セマンティクスと操作

Webは既存の `a.map-card` に素材画像を内包する。移動・拡縮・ホバーはリンクと画像が一緒に変化する。画像の上に別の透明リンクを重ねない。リンクの名前は「ゲームのおすすめへ」等とし、リンク内画像の空altとリンク自体の名前を区別する。

非操作の木・鳥・背景・波形・パターンは読み上げ・フォーカス対象外。さすけ・ぶくろちゃんは装飾的に見えても操作要素であり、既存の `.map-decoration-control` のbutton、操作名、Tab到達、Enter/Spaceによる反応、focus-visibleを維持する。画像だけを空alt/aria-hiddenとし、buttonやその祖先へaria-hidden/inertを付けない。Figmaに反応がないことを理由にimgへ置換しない。既存1600ms/1100msの動作時間と連続クリック時の再始動を維持し、動き低減時もボタンの存在と操作可能性は失わせない。

6スポットとX・イラストの行き先はSDD第4節の表を正本とする。アンカー化する6点から旧target/rel等の外部遷移設定を取り除く。YouTube画面・枠・統計表示は同一アンカーの中に維持し、mapリンクのhrefは動画データ更新で動画URLへ戻さない。カードのhref更新と混同しない。

見出しにはヘッダー実測高＋余白のscroll-marginを設定する。JS補助は通常リンクの意味を保持し、必要な `tabindex="-1"` による到着見出しへのfocus、reduced-motion、連続選択と手動中断に対応する。到着見出しに青いoutlineや選択状態の追加装飾は表示しない。リンク・ボタンのキーボード操作用focus-visibleは維持する。focus時のスクロール二重実行と履歴二重追加を避ける。JS無効でもアンカーとして移動できること。

通常ホバーは現行 `.map-card:hover { transform: translateY(-3px) }`、160ms ease。ホバーラベル・色面・囲い・新しい影を追加しない。キーボードfocusは輪郭で判別できるようにする。さすけ1600ms／ぶくろちゃん1100msの既存ボタン反応、鳥、YouTubeの10秒周期表示と次画像準備は機能を維持する。reduced-motion時の低減は別に確認する。

### 3.3 YouTubeの重ね合わせ

新しい外側の配置だけを共通マップ座標へ合わせ、内部は現行実装の3層を引き継ぐ。外側は1つの `a.map-link-youtube[href="#youtube-title"]`、内部画像・統計はpointer-events:noneとし、看板・画面のどちらを選んでも同じ移動になる。背景を追加のリンクや透明ヒット領域にしない。

| 重なり | 現行要素 | 保持する役割 |
| --- | --- | --- |
| 背面 / z0 | img.youtube-screen-background、map_youtube_bg.svg | 黒い画面下地。上下の不足や動画切替・decode待ちを透かさない |
| 中間 / z1 | span.youtube-screen内のyoutube-thumb群・youtube-stats | 既存の画面クリップ、傾き、登録者数表示、10秒周期と画像準備 |
| 前面 / z2 | img.youtube-frame、map_youtube.svg | 看板の外形・枠。背景と動画を覆う箇所を維持 |

現行CSSの背景 `translate(-4%, 1%)`、screenのpolygon、サムネイル/統計のskewY・scaleは調査時の比較基準として記録し、新しい枠へ無条件で二重適用しない。新枠の元画像余白・正規化後の座標へ変換し、PC/SPで同じ内部変換を共有する。Figmaの静的2画像をそのままWebのレイヤー数と解釈しない。背景SVGは新素材の生成ではなく既存の保持対象である。

動画3枠と統計の各状態、画像decode遅延/失敗、切替途中、hover/focusを検証し、黒下地が画面内を覆い、枠外へ出ず、枠との隙間がないことを確認する。動画更新後も外側hrefはアンカーのままとする。既存のSafari向け影・輪郭対策も保持し、Chromeと利用可能なSafariで確認する。画像に含まれる黒帯等の原本表現と、画面下地の欠落を混同しない。

### 3.4 拡大時の画像解像度

レイアウトを先に既存WebPのピクセル数へ合わせない。G01/G06で座標と対応画面の最大描画寸法を固定し、共通座標から変換した各画像の実描画幅・高さを実ブラウザで記録する。必要ピクセル数は `ceil(変形後の最大CSS描画寸法 × 対象DPR)`。画像全体の透明余白を含む寸法と不透明な絵の境界を混同せず、元SVGを切り抜かない。

主判定は1440×900・1366×768・1280×720・1920×1080、SP320/390/430と境界幅のDPR1/2。DPR3は既存性能設計と同じく画質の目視確認を別記する。G06では基準外の大画面に対する最大描画寸法または追加解像度の選択も確定し、未検証の無制限拡大を採用しない。

| 素材 | 現行配信用 | 保存済みFigma座標から1920×1080/DPR2へ換算した必要幅 |
| --- | --- | --- |
| ゲーム | 512×512 WebP | 580px以上 |
| グッズ | 512×512 WebP | 604px以上 |

上表はヘッダー72・上下24・Hmap960と現行Figma素材幅からの計算値で、Webの新画面実測や候補採用済みを意味しない。最終座標・CSS変換で値が変われば再計算する。他の画像も同じ判定を行う。

不足分だけ既存SVG原本から必要解像度のWebP候補を作り、字形・透過縁・色・比率を比較する。元SVG・地理・クリック範囲・アニメーションは変更せず、品質・容量・LCP/CLSを既存性能設計で再判定する。初期候補は既存と同じ生成器・品質設定。容量超過時はresponsive候補等を比較して採否を記録し、画質を黙って落としたり、必要解像度未達を合格にしたりしない。

採用時は新しいSHA付きURLとmanifestの寸法・source SHA・bindingを更新し、旧出力はadd-onlyで保持する。CSS/JSの再生成だけでは画像解像度は変わらないため、画像候補の比較・採用をW07の独立した入力とする。

### 4.2 テキスト・ラベル

既存書体はFigma `KeinannPOPjp / Black`、Webでは既存の `KeinannPop` エイリアスと配信フォントを使う。CSSエイリアスとFigmaのファミリー名が異なることを、別書体と誤認して置き換えない。

| 説明 | 15/23 | 最大2行、46px、元データがある場合のみ |

C2はニュースの画像直下だけ。GAME #FFE49A、YOUTUBE #F9CCD4、NOTE #CCE7D7、採用済みのSUZURI #FFE8C9、LINE STAMP／LINE EMOJI #DFF4EC。単一カテゴリ枠に分類を繰り返さず、PLAY NOW/GAME LIST/LATEST VIDEO等の装飾ラベルは設けない。下層の「公開中／準備中」バッジ・プレイ情報・キャラ特徴タグも第21節の追加承認で撤去するが、準備中カード自体や説明・非操作状態は維持する。TOPキャラクターは名前最大2行・中央、犬タロー2種の説明を追加しない。見出し・名前背景・操作ボタン・ゲームHUDは装飾ラベルの撤去対象ではない。

通常のカードは実リンクとH3を使い、文字を画像化しない。省略した全文は元データ・リンク先に保持する。価格は日付へ置換せず、現行商品情報を維持する。

### 4.3 3つの生成経路

| 経路 | 主な実装点 | 必須の対応 |
| --- | --- | --- |
| ソース初期HTML | index.html | 静的カード、キャラクター、フォールバックの構造・ラベル |
| 実行時更新 | home.jsのcreateLatestCard/renderLatestCards/renderLatestNews | カテゴリ名そのものと表示有無を分離し、ニュースだけ分類を表示。すべての通常画像をcontainにする |
| 公開ビルド時 | scripts/lib/home-youtube-snapshot.mjs | 初期YouTubeカードとニュースの画像・分類・テキストを同じ契約に揃える |

表示用の分類を省いても、安定キー `category:id/url` やデータ分類は消さない。署名・画像ノード再利用・scrollLeft維持を引き継ぐ。ニュースはゲームと取得済みYouTube/note/SUZURI/LINEの全件を候補にし、更新日時（なければ公開日時）の降順、重複URL除去後の最大12件とする。同日時は入力順を維持し、日時不明は末尾。取得日時fetchedAtを新着判定に使わず、架空の日付も付けない。カテゴリ別の1件制限、埋め草、ニュースのmoreカードは設けない。通常枠は現行最大5件＋5件超の場合だけmore、初期YouTubeはJS無効時最大3件という取得・初期表示契約を変更しない。ニュースの12件は取得済み候補からの表示上限であり、各サービスから12件ずつ取得する変更ではない。

「すべて見る」はニュースを除く6枠に設ける。2列PCは見出し行の右でgap16、SPと幅不足による縦積み時は見出し下の右。第2.3節の必要幅判定を共有する。キャラクター→pages/characters.html、ゲーム→games/、YouTube→既存チャンネル、ブログ→note.com/erinui、グッズ→suzuri.jp/erikanuinui、LINE→既存作者ページ。moreカードとの重複があってもデータ契約としていったん保持し、整理はG05で判断する。

## 7. データ・SEO・配信の保持 TOP-11〜14
