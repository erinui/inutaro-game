## 1. 前提と成果物

[作成方法](figma-reproduction-method.md)に従い、[デザイン設計書](screen-design-specification.md)のS01〜S07を再現する。順序は**キャラクター紹介 → ゲーム一覧 → 案内4ページ → ゲーム本体**。静的ページで共通表現の品質を固めてから、状態制御の必要なゲームへ進む。

資料承認後の「計画に従って進めて下さい」を受け、以下の制作工程を実施した。P0の設計時基準と、P1以降の制作・検証証拠は別ディレクトリで保持する。最新の検収状態と実フレームへのリンクは制作状況を参照。

成果物は固定幅の視覚資料。現行と同じ字形の文字輪郭、図形、画像、状態見本、リンク一覧、検証記録を含む。TEXT化・動作するプロトタイプ・新しいサイト機能・GitHub反映は含めない。

## 5. ゲームの実証ゲート

| ゲート | 試験 | 合格条件 | 不合格時 |
| --- | --- | --- | --- |
| GATE-A 描画 | DOMとCanvasで使う書体の必須ゲートを通し、タイトル・プレイ中のCanvasを取得 | 対象faceのロード成功記録があり、非空で、画像・文字・ゲーム場面がブラウザと一致 | フォント／画像ロード・Canvas取得・DPRを確認。代替書体や無地画像では進めない |
| GATE-B 分離 | Canvas画像にHTMLのHUD/ボタンを重ねる | 四隅とUIが一致し、二重描画・欠落がない | Canvas領域の合成へ縮退可能か検討。編集制限が増える場合は採用前に確認 |
| GATE-C SP | coarse＋横向きと縦向きで取得 | ジャンプ左・スティック右、90deg回転、余白・パネルの見え方が一致 | 幅だけでなくpointer・orientation・dvhを確認 |
| GATE-D 状態 | FIX-INITIAL / FIX-CLEAR / FIX-HAZARDから対応するG01〜G10を取得し、環境別に再取得 | 基準IDと取得地点が全状態に対応。clearとhazardは別プレイ。950ms待機、hidden、時刻・位置、合計と内訳が整合し、同一基準のPC/SP結果を再現できる | テストページだけで時刻/乱数/入力を制御する方式を検討し、再試験。異なるプレイの値を流用しない |

OSネイティブ共有ダイアログ、実SNSへの投稿、端末固有のダウンロードUIは対象外。ゲーム数値の再現に失敗した場合は架空の結果を手入力せず、未完了項目として残す。

## 6. 画面ごとの制作手順

各画面で以下を繰り返す。作成途中にソースが変更された場合はハッシュを再確認し、基準を再取得する。古い基準と新しい表示を混在させない。

1. 設計書の画面ID・構成・文言正本・状態を確認し、今回のURLと基準寸法を確定する。
2. フォント必須ゲートを通し、実ブラウザの表示とDOM記録を取得する。CSSの定義値だけでなく実寸・改行・ロード成功を見る。
3. PCからSVG／レイヤーへ変換し、中間SVGの描画を確認する。最小の代表領域で透過・文字を検証する。
4. Figmaへ取り込み、セクション・画像・文字輪郭を命名する。全画面の単一画像で置き換えない。
5. PNGを書き出して基準と比較する。差の原因をソース、変換、Figmaの3段階に分ける。
6. SPはSPの実表示から別途作成する。PCを縮小して済ませない。
7. 状態値の確定を待って補足を作成し、対応フレームID・取得条件を記録する。ゲームは基準プレイID・環境別再現手順・取得地点を`fixtures.json`から参照する。
8. 下記受入チェックを画面単位で完了し、次画面に進む。

## 10. リスクと対応

| リスク | 予防・対応 |
| --- | --- |
| ブラウザのフォント失敗を見逃す | fonts.readyや例外0件では合格にしない。必須ゲート失敗で取得・変換・取り込みを止め、配信修復後に再取得 |
| Figma書体が使えない | TOPと同じ輪郭を既定にする。別フォントへの無断置換をしない |
| 半透明が薄くなる | マスク変換履歴を調べ、白色アルファ化済みの対象だけALPHAに設定 |
| 1px程度の累積ずれ | 全computed寸法の固定を避け、変換前後・セクションごとに比較 |
| メニュー・動作の途中を撮影 | 固定待ち時間のみでなく、aria・class・transform・hidden・時刻を確認 |
| SPの原文折り返しが好ましくない | 現状再現と改善提案を分ける。今回の制作中にソースを変えない |
| ファイルロック・連携上限 | 作成先・権限・利用可能な経路を再確認。取得や資料整理は継続し、書込不可を隠さない |
| 大きいSVG・ゲーム合成 | 最小サンプルで実証し、必要なら領域単位に分割。全画面の編集可能性を偽らない |
| 古い生成コードによる消去 | 全削除処理を再利用しない。対象ID・バックアップ・明示書込を必須にする |
| 動的データの更新 | 保存データ・ハッシュを固定し、制作中に取得バッチを動かさない |
| ゲームの結末・環境別データの混在 | 初期・クリア・hazardを別IDで管理し、各状態から取得地点まで追跡。PC/SPは環境別再現を検証し、未確定値を手入力で補わない |

## 11. 完成時に残す資料

画面ごとのFigmaリンク、main/stateの実ID、表示条件、基準ハッシュ、フォント成功記録、素材参照、全文台帳、PNG比較、残差表、検証日時を保存する。ゲームは基準プレイID・環境別再現手順・状態の取得地点も保存する。設計IDから該当Figmaと証拠へ辿れる一覧を作る。

資料状態は「計画 → 実証済み → 作成中 → 確認待ち → 完了」で管理する。P0の設計基準と、P1以降の制作証拠を混同しない。

制作時の変更は、新規ページ内の画面別整理、ゲームの実測値・背景効果・縦持ち変換手順。46フレームの範囲は変更していない。今後の再制作はソース差分確認とフォントゲートから始め、固定IDで該当画面だけを更新する。
