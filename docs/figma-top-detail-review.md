## 指摘事項

### R1 / P2 / 実装: 小さいSPではカード自体の右端が切れる

- 対象: 全カルーセル。`home.css:1397`の`flex-basis: min(84vw, 330px)`と、`home.css:959`の横スクロール領域。
- 320px幅では、トラックの表示幅が260pxなのにカード幅が268.796875pxとなる。1枚目の右側約8.8pxに加え、影もクリップされる。画像枠とカードの右ボーダーが同時に見えない。
- 390px幅ではトラック330pxに対してカード327.59375px。次カードの開始位置は371.59375px、クリップ端は360pxなので、次カードの見切れによる横スクロールの手掛かりが出ない。右側の5pxの影にも十分な余白がない。
- 原因: カード幅を親の表示領域ではなく、ビューポートの`vw`から算出している。左右のセクション余白・トラック余白を差し引けていない。
- 対応方針: トラックの利用可能幅を基準にカード幅を決める。カード全体と影を収めたうえで、次カードが16〜40px程度見える余白を別に確保する。320/375/390/430pxで確認する。
- Figma390px版にも現在の実装の「次カードが見えない」状態が再現されている。実装を直す場合は、その後にSPデザインを同期する。
- [320pxでの実表示](/Users/ishiharajunpei/.codex/visualizations/2026/06/14/019ec45c-b660-7d62-bd76-e50427b869e0/figma-top-review-20260912/sp320-card-clipping.png)

### R2 / P2 / Figma: 「カルーセル末尾」が末尾位置になっていない

- 対象: [PC YouTube / カルーセル末尾](https://www.figma.com/design/XEgScjFWiQZTUZcnbn24RO/?node-id=2228-48718)。少なくともこのフレームで確定。
- Figmaには3本目の途中、4本目、5本目、6枚目の一部が写る。「まだまだあるよ」カードの大半が右端で切れ、次へボタンも有効な表示のまま。
- 現行実装を末尾まで移動した場合は、4本目・5本目・「まだまだあるよ」の3枚が全体表示される。実測は`scrollLeft=1014`、`scrollWidth-clientWidth=1014`。即時・120ms後・1秒後とも同じ値だった。
- これは実装の末尾レイアウト不良ではなく、Figma用の状態取得結果の不備。過去の取得処理は末尾位置を実測せずに撮影していた。取得時の再レイアウト・スクロール状態確定のどちらが直接の引き金だったかは未確定。
- 対応方針: 実データ反映後に末尾へ移動し、`abs(scrollLeft-maxScroll) <= 1`、次へボタンの無効状態、複数フレームでの位置安定を確認してから再取得する。他の「末尾」フレームも同じ条件で再検証する。

### R3 / P2 / Figma: さすけの「復路」が反転前の状態

- 対象: [さすけ / 復路](https://www.figma.com/design/XEgScjFWiQZTUZcnbn24RO/?node-id=2228-48739)。往路の作成元画像も再取得候補。
- Figmaの復路画像は通常時と同じ向き。実装を1200msで止めると左右反転し、元位置から右へ約7.09px・下へ約5.99px移動した姿になる。
- 実装の該当箇所: `home.js:22`のクリック処理は`requestAnimationFrame`の中でクラスを付ける。`home.css:546`でアニメーションを開始し、`home.css:657`の後半に反転を定義している。
- 取得処理はクリック直後にアニメーション時刻を設定しており、その時点では新しいアニメーションがまだ作成されていない可能性がある。今回、`sasukeWalkPath`の存在を待ってから1200msを設定すると、実装どおりの復路になった。
- 対応方針: 対象のアニメーション名・生成を確認し、歩行経路と画像の向きの両方へ同じ時刻を設定する。CSSクラスを消すタイマーにも配慮し、状態の実測値と画像をセットで保存する。

### R4 / P2 / Figma: 透過装飾・影の濃さと輪郭が異なる

- 対象: PC/SPのマップ説明内のピンク色の円、各セクションの円形装飾、キャラクター画像の影など。
- 同じ座標のRGB値を比較すると、以下のようにFigmaが薄い。文字のアンチエイリアスだけでは説明できない、面の色の差がある。

| 位置（PCフレーム原点からのpx） | 実装 | Figma |
| --- | --- | --- |
| マップ説明内、x1200 / y515 | `#FFDDE7` | `#FFEFF0` |
| ゲーム背景、x1175 / y2390 | `#FFEEB8` | `#FFF7DD` |
| ブログ背景、x1160 / y3655 | `#CFF3D9` | `#ECFAEC` |

- 円の境界にも低解像度のマスクを拡大したような段差が見られる。キャラクター紹介のぬいぐるみ・えりかの画像周辺では、実装より影が弱い。
- 元実装: `home.css:348`のピンク円は不透明度0.45。各セクションは`home.css:871`以降。キャラクター画像の影は`home.css:1100`以降。
- 原因の切り分け: 中間SVGをブラウザで描画した画像では、PCのx1200/y515は実装と同じ`#FFDDE7`だった。Figma書き出しでは`#FFEFF0`へ変わるため、この円の色差はSVGのFigma取り込み・マスク解釈を含む段階で発生している。透明度の重複適用など、内部の具体的な原因は追加確認が必要。
- 対応方針: 単純な円はFigmaの図形で元の色・透明度を直接指定するか、装飾と下地を一度だけ合成した画像にする。影付き画像はアルファの二重適用を避け、同じ寸法で再比較する。サイト側の色・影は変更しない。

### R5 / P3 / Figma: SPのゲーム枠以降が約1px上にずれる

- 対象: [SP主画面](https://www.figma.com/design/XEgScjFWiQZTUZcnbn24RO/?node-id=2228-45703)のゲーム・YouTube・ブログ・グッズ・LINEスタンプ付近。
- 見出し周辺の暗色ピクセルを±4pxで照合すると、PCの主要見出しは補正0pxで最も一致。SPは冒頭〜キャラクター紹介が0px、ゲーム以降の5見出しがY=-1pxで最も一致する。並列画像でも上端・下端に差が見える。
- SPブログのサムネイル上端には、実表示では目立たない薄い横線もある。1px程度の境界・合成丸め誤差として再確認する。
- 原因候補: 小数pxを含む画面配置を中間PDF/SVGへ変換する際の丸め。全長フレームの高さが同じでも、内部の要素座標が一致するとは限らない。
- 対応方針: 全体を一括移動しない。ずれ始めるセクション以降を実測座標へ合わせ、見出し・カード・画像・フッターを同時に確認する。

## 編集可能性と検証の制限

- 主画面内のTEXTノードはPC/SPとも0件。COMPONENT/INSTANCEも0件。本文検索・コピー・文字入力・font-sizeの直接変更はできない。これは前回から明示済みの制限だが、今後のデザイン編集用データとしては大きな制約になる。
- PCは4599子孫ノード、SPは2993子孫ノード。位置関係は固定座標であり、任意幅への自動レイアウトやコンポーネント管理を備えた設計データではない。
- 27補足状態の存在・親内の寸法は確認できたが、今回R2・R3が見つかったため、「27件すべて意味的に正しい」とは判定しない。残りも状態確定条件付きでの再取得・確認を推奨する。
- 実装は320/390/768/1024/1440pxで描画した。各幅で画像48点のロード失敗0件、JavaScript例外0件、ページ全体の横幅超過0件。ただし内部カルーセルのクリップ不良（R1）は別問題。
- 今回の基準ブラウザはローカルChrome。Safari実機、別OSでの字形差、リンク遷移先全ページ、外部APIやGitHub Actionsの健全性は対象外。

## 推奨する対応順

1. 実装のSPカード幅をトラック基準に修正し、小画面でもカードと影が収まる状態にする。
2. その修正後の表示でSP主画面を同期する。現行再現を保管するなら既存フレームは残し、修正版を分ける。
3. カルーセル末尾・さすけ復路などの補足画像を、状態の数値確認後に取り直す。
4. 円形装飾・影の透過処理を個別補正する。サイト側の色をFigmaの誤差へ合わせない。
5. SPの1px前後の座標・境界誤差を補正し、文字の折り返しを含めて再比較する。
6. 継続的なFigma編集に使う場合は、別工程で元書体のTEXTレイヤーとコンポーネント化を行う。
