## 1. 進め方と公開単位

各工程は小さな差分で実装・検証し、工程ごとにsource/データSHAと結果を残す。直前工程の合格版を比較基準にして施策の効果を分け、P0の原始baselineも保持する。自動更新データの変更を容量改善の効果に加算しない。

| 公開単位 | 含む工程 | 目的 | 公開条件 |
|---|---|---|---|
| R1 | P0〜P2 | 配信生成基盤とマップ軽量化 | SVG1枚比較→8枚、共有表示、生成資産・旧URL・ビルドが合格 |
| R2 | P3a→P3b | フォント表示と容量 | swap単独と分割を別記録。分割未達ならswapのみの効果を明記して切り出し可 |
| R3 | P4→P5 | YouTube整合・その他画像・読み込み | 互換consumer→producerの順、更新失敗と6件対応、スライドが合格 |
| R4 | P6→P7 | 限定長期キャッシュ・統合 | immutable/更新反映/切り戻しと総合性能が合格 |

R1〜R4は論理的な公開単位であり、同時公開も可能。各単位の合格証跡を用意してから公開する。設計・計画の作成は、push・デプロイ・サーバー設定変更の実行を含まない。公開を進める際はその時点の利用者指示と承認済み範囲に従う。

各公開単位には対応する復旧artifactも含める。直前合格版コード・最新正常データ・保持資産の和集合・整合したmanifestを組み合わせ、公開前にビルドと遅延取得を確認する。過去releaseへ直接戻せるとは仮定しない。

### 1.1 工程の合格と最終達成

HP-T11は[設計書3.1節](home-performance-design.md#31-工程別判定と最終判定)の `stage` / `final` を使う。P1〜P6は当該施策の機能・表示・LCP/CLS回帰なしと工程固有条件を判定し、総量1MBを全工程の前提にしない。画像採用は各100KB以下、P3b採用は初期フォント合計100KB以下を工程固有条件とする。swapだけのP3aには容量削減を要求しない。

P7/P8で全体容量・フォント・LCP・CLS・再訪の最終目標を `final` 判定する。段階合格・対象施策保留・全体目標未達を別々に記録する。未達を残して部分改修を公開判断へ提示する場合も、final合格や全体改善完了とは表現しない。

## 12. 切り戻し条件・手順

| 兆候 | 対応 |
|---|---|
| 主要画像/フォント404、誤画像、文字欠落 | 対象単位の公開を止め、直前合格版参照へ戻す |
| 最新JSONと画像の対応崩れ、正常データ消失 | 更新producerを直前互換版へ戻し、正常snapshotと全参照画像を復元 |
| メニュー/リンク/ゲーム開始の回帰 | 対象consumerを直前合格版へ戻してsmokeを再実行 |
| immutableの誤適用・誤内容 | 不変資産は新ハッシュ、更新JSON/画像は新しい復旧URLへ変更。再検証設定とconsumer・snapshot・以後のalias更新を一体で修正 |
| LCP/CLS悪化、容量未達のみ | 原因を工程比較で特定し、当該施策を戻す/保留。達成と報告しない |

1. 対象releaseと症状、JSON/画像SHAを保存する。
2. 直前合格版ソース・有効manifest・変換仕様に、最新の正常データと保持資産の和集合を組み合わせ、復旧releaseをクリーンビルドする。
3. 現行/直前版/保持期間内の新旧ページから要求される全URLとSHAを公開前に照合する。過去releaseへ直接戻す場合も同じ集合の存在と互換性を事前に証明し、不足/未確認なら直接復帰せず復旧releaseを再公開する。
4. 更新JSONが誤キャッシュされている場合、設計書10.2節に従って復旧ID付きの新JSON URLと必要な新画像URLを用意する。snapshotとaliasの入力を同じcanonicalへ揃え、ビルドでaliasを再生成してconsumer参照を切り替える。collectorの許可パスは広げない。ヘッダー修正だけで解決済みとしない。
5. 新規ページ・開いた旧新版ページ・遅延画像/フォント・キャッシュ・JSONの次回更新を確認する。旧ページresolverや誤キャッシュHTMLの自動復旧は保証せず、通常再遷移または新文書URLで復旧できる範囲を記録する。
6. 復旧結果と再着手条件を本書へ追記する。browser cacheの消去を利用者へ一律に要求しない。
