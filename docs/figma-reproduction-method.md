# 現行サイトをFigmaへ再現する作成方法

更新日: 2026-09-12 / 方法書 v1.2

改訂: v1.1のフォント必須ゲート・ゲーム基準プレイに加え、下層画面制作で実証した回転倍率補正・背景ぼかしの保持・ページ上限対応を追記した。

2026-10-10名称改訂の補足: 正式なサイト名は「エリカッテシティ」。採用仕様は[総合仕様2.1](site-specification.md#21-サイト名称の設計ルール)、改修対象は[文言反映設計](figma-copy-change-plan.md)を参照する。本書の現行ソース再現手順では旧名称を含む実測証拠を改ざんせず、採用仕様との未反映差分を記録する。改修デザインではPC/SPの共通名称と編集可能テキストを使用し、背景は文字幅へ追従させる。過去の再現フレームを無断で再生成・上書きしない。

## 1. 資料の位置づけ

TOPの調査・実証・制作・レビュー・修正から、別画面でも再利用できる方法を整理した。設計変更の手順ではなく、**現行ローカルの表示を再現する手順**である。

資料の順序:

1. 本資料: どの方法で、どの制約のもとで作るか。
2. [画面デザイン設計書](screen-design-specification.md): 何をどの表示・状態で再現するか。
3. [Figmaデザイン作成計画書](figma-screen-production-plan.md): 設計項目をどの順序で作り、何を検証するか。

実績の根拠: [TOP実証](figma-top-feasibility-report.md)、[制作状況](figma-top-production-status.md)、[詳細レビュー](figma-top-detail-review.md)、[修正結果](figma-top-fix-results.md)。過去の計画と実施結果が異なる場合は、最新の修正結果を優先する。

## 2. 完成物と制約

| 項目 | 標準方針 | 実績・制約 |
| --- | --- | --- |
| 主画面 | PC/SPを別々に実描画し、図形・画像・文字輪郭のレイヤーで再現 | TOP・下層で実証。画面追加ごとの書き出し比較は省略しない |
| 本文 | 同じ字形・改行を優先 | TOPではFigma側の書体ロードができずアウトライン化。直接文字入力できない |
| 画像 | 素材単位を可能な限り保持 | SVG内の埋め込み画像はラスタ画像のまま。SVGであることは全面ベクター化を意味しない |
| 影・複雑な効果 | 小さな単位で合成画像を許容 | 合成部分では影だけの編集ができない |
| 補足状態 | 実ブラウザの静止画像をCSS実寸で配置 | 自動再生・クリック動作を持つプロトタイプではない |
| レイアウト | PC/SPの固定幅資料 | 任意幅へ自動追従するコンポーネントではない |
| Canvasゲーム | Canvasは画像、HTMLのUIは文字輪郭・図形、背景ぼかしは局所画像 | 下層制作P6で専用試験を実施。背景効果の内部は個別編集できない |

本文TEXT化・変数連携・コンポーネントライブラリ・動作するプロトタイプは別工程。見た目を優先した成果物を「完全に編集可能」と表現しない。

## 3. 判断の優先順位

1. 同じソース・保存データ・表示条件によるローカルブラウザの実表示。
2. DOMの文言・計算済みCSS・画像参照・ゲームの状態値。
3. 現行HTML/CSS/JSの定義。
4. 既存の仕様書、ワイヤー、過去のFigma。

CSSの一部分だけで寸法を決めない。後勝ち、詳細度、疑似要素、最小幅、変形後の位置を確認する。過去の意図と現状が異なっても、再現作業中にサイトやFigmaだけを独自に改善しない。問題は別の改善候補として記録する。

## 4. 準備と基準記録

| 記録項目 | 内容 |
| --- | --- |
| ソース | コミット、未コミット差分、使用HTML/CSS/JS・データ・画像のSHA-256 |
| 表示 | URL、query、hash、ビューポート、DPR、ブラウザ、OS、pointer、orientation |
| データ | 保存JSONとローカル画像。取得日と画面上の日付を区別 |
| 状態 | メニュー、フォーカス、scroll位置、アニメーション時刻、ゲーム結果 |
| 寸法 | 全長、主要領域のx/y/w/h、文字行の矩形、画像のnatural寸法と表示寸法 |
| Figma | fileKey、pageId、rootId、子ノードID、編集可否、ロック、更新前バックアップ |

環境変数ファイル・APIキーを記録やFigmaへ含めない。ローカルサーバーは公開素材を許可リストで配信し、127.0.0.1に限定する。検証のために外部データ更新やGitHubへの送信を行わない。

## 5. ブラウザ取得の標準手順

1. 通常ページはPC1440×900、SP390×844 CSS px、主画面DPR1で表示する。ゲームの条件は設計書に従う。
2. HTTPで対象URLを開き、レスポンスとJavaScript例外を記録する。ファイル直開きの制限を基準表示に持ち込まない。
3. 下記のフォント必須ゲート、画像decode、動的要素数・内容を確認する。`document.fonts.ready`、network idle、一定秒数の待機だけで準備完了としない。
4. 遅延読み込みを完了させ、初期scroll位置とメニュー状態を戻す。遷移・hoverの途中になっていないことを確認する。
5. 主画面、DOM、文言一覧、画像一覧を同じ状態から保存する。短いページはviewportの下端まで含める。フッターを勝手に画面下へ移動しない。
6. 補足は対象領域をDPR2で取得してよい。Figmaでは画像ピクセル数ではなくCSS実寸で配置する。
7. stickyヘッダーや固定要素が全長画像に重複していないことを確認する。

### フォント必須ゲート

読み込み失敗の実証では、フォント通信を遮断しても`document.fonts.ready`が解決し、`document.fonts.status`は`loaded`、computed styleのfamilyは`KeinannPop`、JavaScript例外は0件だった。一方、対象の`FontFace.status`は`error`だった。待機完了と指定書体の取得成功を区別する。

1. DOMとCanvasで使用するfamily・style・weightと、実際の日本語・数字・記号を対象にする。Canvasの指定はcomputed styleだけでは取得できないため、描画コードも確認する。
2. 対象familyを単独指定して`document.fonts.load()`を実行する。例: `document.fonts.load('400 16px "KeinannPop"', '犬タローの虫さんまって×2')`。各使用weight/styleについて、例外なし・返却配列が空でない・返却された対象faceがすべて`loaded`であることを必須にする。
3. `document.fonts`内に対象familyの登録faceが存在し、使用対象のfaceが`loaded`であることも照合する。`document.fonts.check()`単独やCSSのfamily名だけで合格にしない。現行の登録はnormal/400で、700・900はブラウザ合成の場合があるため、900専用ファイルの存在を条件にしない。要求weightと実際に解決したfaceを分けて記録する。
4. family・要求style/weight・解決faceのstyle/weight/status・取得成功したフォントURLとSHA-256・失敗理由を`fonts.json`へ保存する。通常ロード成功と、検証用ページでwoff2/ttfを両方遮断した失敗の2条件で判定を試験する。
5. 未登録、空配列、読み込み例外、対象faceの未完了・errorのいずれかなら、基準画像の採用、PDF/SVG生成、Figma取り込みを停止する。診断画像は失敗証拠として分離する。配信や参照を直して再取得し、代替書体のまま進めない。

このゲートは各ページ・各取得環境で通す。動的に別書体が現れる状態も再確認する。取得成功は字形の完全一致まで保証しないため、原文の字形・改行の目視照合も必要。**ブラウザでの読み込み失敗**と**Figmaで書体が利用できず輪郭を使う判断**は別問題であり、後者で前者を許容しない。

### 状態の確定条件

| 状態 | 撮影前の確認 |
| --- | --- |
| SPメニュー | `aria-expanded`、開閉クラス、visibility、opacity、変形の終端 |
| カルーセル末尾 | scroll位置と最大値、最終カードの見え方、次ボタン無効化、複数フレームでの安定 |
| アンカー遷移 | scroll停止、stickyとの重なり、`scroll-margin-top`、ページ末尾での上限 |
| CSSアニメーション | クリック後に対象クラス・animationが作られたことを待ち、対象名だけ停止・時刻設定 |
| ゲーム | 設計書の`FIX-INITIAL`・`FIX-CLEAR`・`FIX-HAZARD`とG01〜G10の対応を使い、描画ループ、状態値、乱数、経過時間、UIのhiddenを確定。CSS animation停止だけでは不十分 |

scroll-snapで理論最大値の手前に停止する場合は、無理に解除して「理想の末尾」を作らない。通常操作で到達する安定状態と数値を記録する。TOP修正時は最大値との誤差1px以内と次ボタン無効化を確認できた。

## 6. 主画面の変換経路

標準経路: ローカルブラウザ → screen表示のPDF → 輪郭SVG → Figmaネイティブレイヤー → PNG再出力 → ブラウザ画像と照合。

1. 変換直前に必要な書体サイズだけ固定する。全要素の計算済みwidth/height/margin等を一律に再設定しない。TOPではその処理がSPの約1pxの累積ずれを生んだ。
2. 固定前後のブラウザ画像を比較する。変換準備によって配置が変わった場合は、Figma取り込み前に処理を直す。
3. PDFはscreen media、背景あり、同じCSS幅、全長を収める高さを指定する。TOPでは末尾余白16pxを加え、複数ページ化を防いだ。別画面でもページ数を検査する。
4. `pdftocairo -svg -f 1 -l 1 -origpagesizes -noshrink -nocenter`で変換した実績がある。意図しない縮小・中央配置を防ぐ。
5. SVGのptをCSS pxへ合わせる。TOPは96/72 = 4/3の変換を使用。出力単位を確認せず常に4/3を適用しない。
6. SVGを一度ブラウザで描画して基準PNGと照合する。この段階で差があれば、Figma側の問題と混同しない。
7. 全長が大きい場合はページ分割を検出する。セクション別取得を選ぶときは、元の座標・背景・sticky・重なりを維持し、継ぎ目を検証する。

### 透過・マスクの重要事項

- TOPではフィルター付きSVGマスクを展開し、必要なマスク画像を白色RGB＋所定のアルファへ変換した。
- **白色アルファ化が済んだマスク**がFigmaでLUMINANCEになっていたため、ALPHAに変更すると薄い円・影が改善した。PCの指摘3地点はRGB値まで一致した。
- 任意のLUMINANCEマスクを一括でALPHAへ変えることはしない。色の明るさで抜きを定義した本来の輝度マスクを壊す可能性がある。変換履歴・塗り・サンプル画像を確認して対象IDを限定する。
- 色と影の補正のために元CSSを薄く／濃くしない。画像内に合成済みの影へFigmaの影を追加しない。
- 円の内部色、境界、キャラクターの半透明な影を別々に検証する。

### ゲームで確定した変換手順

1. 時刻・乱数・入力をテストページ内で制御し、実装の`update`・`collide`・描画関数を通して基準状態に到達する。スコアや虫の座標を完成値へ書き換えない。各環境で繰り返して同じ表示値になることを確認する。
2. 有限時間のパネル出現アニメーションを終端へ進める。参照PNG、Canvas PNG、状態値を先に保存する。変換準備後の画像を参照の代わりにしない。
3. 変換中だけCanvasを保存済み画像で表示する。部分スクリーンショット取得に伴うresizeでCanvasが消去される影響を防ぎ、原寸を保つ。
4. PDFでは`backdrop-filter`が失われるため、該当パネルの内容を一時的に非表示にして背景効果だけを撮影し、その背景を局所画像として置く。文字・ボタンは復元して輪郭/図形として変換する。元のフォーカスも復元し、準備前後の差を比較する。縦持ち背景画像は回転を戻して同じCSS領域へ配置する。
5. PCのrelative配置をabsoluteへ変更しない。SPのfixed配置、dvhを参照する寸法、見えないブラウザ用スクロール余白だけを変換用に固定する。元のstyleを保存し、撮影後に復元する。
6. 今回のSP PDFには追加の空白ページが発生した。PDF端2pxの描画端数を除いたRGBの標準偏差0を検査し、空白だけを除外した。内容のある2ページ目を無条件に捨てない。第1ページ全域も参照PNGと比較する。
7. 縦持ちでは回転前の横幅を基準に印刷時の縮小が起きた。CanvasのSVG行列`matrix(0, 0.5, -0.5, 0, ...)`を確認し、今回の2状態は1pt→2CSS pxで復元した。通常の4/3倍率をそのまま使わず、Canvasの一意性・バッファ寸法・行列をアサートする。別ソースへ固定倍率を無検証で再利用しない。
8. Figmaへの補正は今回追加した22フレームだけをIDで限定し、非表示バックアップを残して子レイヤーを更新する。主フレームIDと寸法を保つ。

これらは撮影・変換専用の処理であり、サイト本体の修正ではない。画面全体を単一PNGにする方法とは異なるが、Canvasと背景効果の内部は画像としての編集に限られる。

## 7. Figmaでの安全な組み立て

1. 既存ファイルとページを読み取り、対象・ロック・利用可能な書体・既存部品を確認する。過去のIDを新画面に流用しない。
2. 利用可能なFigma連携を優先する。TOPでは連携の利用上限後、通常のデスクトップ開発プラグインを使用した。新画面でも利用可否・権限は着手時に再確認する。
3. 既存TOPとPage 1には触れず、新画面の専用ページ／フレームを作る。試験ノードは本番成果物と区別する。
4. PC/SP・補足列など関係する外枠はAuto Layoutで整理し、ブラウザ再現部分は固定座標を保持する。再現用の座標を自動レイアウトへ無理に変換しない。
5. ヘッダー、導入、本文、カード、画像、フッターでレイヤーを命名する。ノード名に画面・状態・内容を含める。
6. 一画面ずつ取り込み、書き出し検証する。主画面を1枚のスクリーンショットだけで完成扱いにしない。
7. 修正時はrootIdを維持し、対象ノードだけ更新する。子レイヤー差し替え前は非表示バックアップを残す。更新対象と除外対象をID一覧に記録する。
8. プラグインのホットリロードで意図せず全体再生成しないよう、初期動作は読取専用、書込は対象確認後の明示操作に分離する。
9. TEXT注記を変更するときは、そのノードが使う書体をロードしてから変更する。終了時は書込ボタンを外し、作業パネルを閉じる。

下層制作時はStarterの1ファイル3ページ上限に達したため、既存2ページを保持し、新しい3ページ目の中で画面別の外枠へ整理した。制作範囲・主フレーム寸法は変えず、プラン変更も行わない。ページ分割の変更は計画書・制作状況へ記録する。

## 8. 品質確認と合否

| 検査 | 判定方法 |
| --- | --- |
| フォント | 必須ゲートの成功記録と実字形を確認。待機完了だけ、代替書体の描画だけでは不合格 |
| 文言 | DOM原文、表示上の改行、省略、句読点、数字、日付、単位を確認。アウトラインでは文字列機械照合不可と明記 |
| 配置 | 同一CSS寸法の画像を並列・重ね合わせ・差分で比較。意図しない系統的な1px移動も修正対象 |
| 画像 | ロード、余白、contain/cover、SVGのviewBox、輪郭の切れ、前後関係 |
| 色・影 | 問題箇所のRGB値と輪郭を確認。背景面積の大きい全体平均だけで合格にしない |
| 状態 | 見た目に加えて状態値・aria・scroll・transformを照合。枚数が揃っただけでは合格にしない |
| 狭幅 | カード本体・影・文字の欠けと、意図した見切れを区別する |
| Figma構造 | root、node数、画像塗り、文字輪郭／TEXT、バックアップ、補足のはみ出し |

配置は主要アンカーの系統ずれ0pxを目指し、サブピクセル由来の差は1px程度を目安に局所判定する。1〜2pxなら自動合格とはしない。画像補間・アンチエイリアス差は残差として記録し、ピクセル完全一致を宣言しない。

## 9. 保存・引き継ぎ

画面別に `source.json`（条件・ハッシュ）、`fonts.json`、`dom.json`、`copy.json`、`assets.json`、`states.json`、`reference.png`、`figma.png`、`diff.png`、`figma-manifest.json`、`verification.md`を保存する。状態ID・source ID・Figma IDを相互参照できる形にする。

ゲームは`fixtures.json`も保存する。基準プレイID、環境別の再現手順、乱数・入力・時刻、取得地点、実測スコア・内訳・終了理由を記録し、各`states.json`から参照する。異なる結末の値や別環境の画像を混在させない。実測前の数値は未確定とし、制作済み扱いにしない。

TOP作業のスクリプト・SVG・証拠は[修正結果の保存先](figma-top-fix-results.md#証拠作業データ)にある。`/tmp`の実行ファイルは永続の手順書に代わるものではない。再利用するときは対象URL・IDをパラメーター化し、全削除・全再生成の古い処理を取り除く。

`scripts/check-home-layout.mjs`はTOPカルーセル専用の回帰テスト。下層画面やゲームまで検証済みと解釈しない。新画面の検証対象と受入条件は次の設計書・計画書に従う。
