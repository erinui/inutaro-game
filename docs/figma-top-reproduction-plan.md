## 0. 実証後に確定した方針

- PC1440px・SP390pxの取り込みに成功。全長はそれぞれ5648px・5642px。画像の取得失敗は両方0件だった。
- 自動取り込みは配置・寸法・画像・元テキストの収集に採用する。完成版としてそのまま採用しない。
- Figma連携環境ではサイト書体のロードが失敗し、実際の書き出しも別の字形になった。「同じ字形で編集可能なテキスト」は現状未達であり、完成前の必須条件とする。
- 同書体の輪郭SVGは生成・取り込み・描画に成功。ただし文字入力ができず、複数行・疑似太字を含む全文での一致も未検証のため、全テキストの自動置換は採用しない。
- 本制作ではまずFigma連携環境に書体を認識させ、実際の新規テキスト作成・編集・描画を再試験する。環境対応ができない場合は、アウトライン／画像化による編集制限を示して採用範囲を確定する。
- 看板の傾き・画像の重なりは取り込めた。マップの影には差が出たが、代表リンクの絵とCSS影を一体にした透過PNGの配置・描画に成功した。影に差が出る素材はこの方法を代替にする。リンク単位の移動・拡縮は可能だが、影単独の編集はできない。全素材とPC/SPそれぞれへの適用後に比較する。
- SVG直接取り込みは成功したが、元SVG内の埋め込み画像は画像のまま残る。「SVGならすべての線が編集可能」とは扱わない。
- 制作完了の判定は、書体と影の問題が解消し、同一サイズでの比較が通った時点とする。

## 1. 目的と基準

現状のローカルソースをブラウザで表示した結果を、PC・SPそれぞれのFigmaデザインとして再現する。今回の対象はTOPのみ。

- 作成先: 「サイトマップ _共有」 https://www.figma.com/design/XEgScjFWiQZTUZcnbn24RO/
- 同ファイルは前段調査で接続・既存ページ `Page 1` を確認済み。着手時に再確認する。
- 正解の基準はローカルの描画結果。過去のワイヤー、公開版、古い資料との違いは現行ソースを優先する。
- 未コミットの `index.html`・`home.css` と新しい `map_sns2.svg` も対象に含める。
- デザイン改善、文言変更、ソース修正、GitHubへの反映は今回の対象外。
- Figma既存の作業フレームは保持し、再現用のページ・フレームを追加する。

## 3. 表示条件の固定

| 条件 | PC | SP |
| --- | --- | --- |
| 基準ビューポート | 1440 × 900 CSS px | 390 × 844 CSS px |
| 操作環境 | マウス、通常表示 | タッチ対応のモバイル表示 |
| 主フレーム | 幅1440px、コンテンツ全長 | 幅390px、コンテンツ全長 |
| ヘッダー | 通常ナビゲーション | メニュー閉状態 |
| カルーセル | 全枠が先頭位置 | 全枠が先頭位置、見切れを維持 |
| YouTube看板 | `?youtubePanel=0` で先頭サムネ固定 | 同左 |

Figmaの寸法はCSS pxを基準にする。スクリーンショットの解像度倍率と混同しない。ブラウザのURLバー等はフレームに含めない。

現行TOPの主要な切り替え幅は760px以下。追加の表示確認は幅375px、430px、760px、761px、1280pxで行う。これらすべてを完成フレームに増やすのではなく、折り返し・切り替え条件の確認に使う。

描画の固定手順:

1. 制作開始時のソース、保存JSON、対象画像のハッシュ・取得日時を作業記録に残す。
2. HTTPのローカル表示を使用する。ファイル直開きによるJSON取得失敗を避ける。
3. YouTube・note・SUZURI・LINEの既存ローカルデータを使用し、自動更新処理は実行しない。
4. フォント読み込み、画像のdecode、非同期カード描画の完了を確認する。固定秒数の待機だけで判定しない。
5. 遅延画像がある場合は各領域を表示して読み込ませ、撮影時にはスクロール位置を戻す。
6. 鳥などのアニメーションを記録した時点で一時停止する。停止操作は検証用ページ上で行い、制作ソースへ永続化しない。
7. 外部画像の取得失敗は記録する。意図した代替表示と通信失敗を区別してから基準画像を確定する。

### マップの注意点

- PCはマップが左、説明カードが右。SPはマップの下に説明カードが並ぶ。
- `.map-stage` は `402 / 639` 比率。PCは最大402px幅、SPは親領域の横幅に従う。
- マップ背景、各リンク、装飾は別レイヤーとし、現在の座標・拡縮・重なり順を記録して再現する。
- SVGのviewBox全体と実際の絵の範囲は異なる。Figmaで可視部分だけに合わせ直すとサイズ・配置が変わるため、透明余白も含めて照合する。
- YouTubeは背景SVG、傾けた画面コンテンツ、前面の看板SVGを区別する。マスクと変形はブラウザの四隅の位置を基準にする。
- X導線は現在参照されている `map_sns2.svg` を使用する。

### カルーセルの注意点

- PCの一般カードは `calc((100% - 48px) / 3)`、キャラクターカードは `calc((100% - 36px) / 3)`。現状の実測幅をそれぞれ採用し、勝手に同一寸法へ変更しない。
- SPは `min(84vw, 330px)` 幅で、矢印ボタンは非表示。親領域でのクリップ・次カードの見え方を再現する。
- 一般の画像付きカードは435px高の指定がある。キャラクター枠には別の高さ設定があるので分けて扱う。
- 画像の16:9枠と、枠内のcover/containの違いを保持する。
- 動的カードは5件まで実データ、6件目がある場合はAND MORE「まだまだあるよ」。存在しない作品でカード数を埋めない。
- 末尾位置は実際のスクロール上限から取得する。件数によって前ページのカードが再び見える場合も現行表示に合わせる。

| 2. Figma準備 | 作成先の再確認、既存部品・スタイル・フォントの調査、再現用ページの作成 | 既存デザインとの配置衝突がなく、使用可能な書体が判明した |

部品化は工程3から行う。現行ソースに対応するヘッダー、見出し、カテゴリラベル、カード、矢印等を再利用可能にする。Figma内に一致する部品があれば再利用し、別のデザイン体系の部品に置換しない。

通常のレイアウトはAuto Layout、マップの絵の重なりなどは絶対配置を利用する。ブラウザcaptureは画像と見た目の参照に使い、編集用フレームと並べて確認する。画像の取り込みが50MB上限等に当たる場合はセクションごとに分ける。

## 7. 書体・表現の扱い

- サイトの `KeinannPop` はCSS上の名称。Figmaのフォント一覧では実フォントのファミリー名・スタイル名を確認する。
- 実証では必要書体のロード失敗と代替字形での描画を確認した。Figma連携環境で書体を利用可能にしてから再試験する。デスクトップへのインストールだけで連携側でも解決すると保証しない。
- 日本語本文は編集可能なテキストを基本とし、字形・行間・幅を確認する。別フォントへ無断で置換しない。
- 書体がFigma実行環境から使用できない場合は、その制約と見た目優先のアウトライン化等の代替案を提示する。編集可能と完全一致の両立を確認前に保証しない。
- SVGは可能な範囲でベクターを保持する。埋め込み画像、フィルター、複雑な変形は個別確認し、必要箇所だけ画像化する。
- 影を含む個別画像は倍率2で取得し、FigmaではCSS実寸で配置する。元素材SVGは別途残し、追加のFigma影を重ねない。YouTubeのサムネイルは独立したままとし、看板の固定部分のみ一体化の対象にする。
- ページ全体を1枚の画像にしたものだけを編集用成果物とはしない。
- stickyヘッダー・説明カードの全長キャプチャでの重複を確認する。Figma主画面では初期位置を再現し、スクロール中の見え方は補足状態で扱う。

## 8. 受入基準

- PC1440px・SP390pxで、全領域の順序、主要座標、画像寸法、余白がブラウザと一致する。
- マップの絵が欠けず、YouTube画面の四隅・黒背景・前面枠の重なりが合っている。
- キャラクターは現行と同じ素材・サイズ・名前になっている。
- 一般カードとキャラクターカードの寸法差、SPでの見切れがソースどおりになっている。
- サムネイルの切り抜き・余白、タイトル行数、カテゴリ、日付・価格が固定したデータと一致する。
- AND MOREの画像枠・ラベル・タイトル位置がブラウザと一致する。
- 文字の欠落、代替フォントへの意図しない切り替え、Figma側だけのはみ出しがない。
- PC/SPキャプチャとFigmaの書き出しを同一スケールで重ね合わせ、領域ごとに目視する。座標や枠は原則1〜2 CSS px以内を目標とする。文字のアンチエイリアスや影の描画差は位置ずれと区別する。
- 完了時は主フレームと補足状態へのリンク、表示条件、既知の再現差を残す。

## 9. 実証後の作業順

1. Figmaで使用できない書体への対応を先行する。既存文字ノードの書体名表示だけでは合格とせず、新規作成・文字変更・書き出しで検証する。
2. 検証用PC/SPフレームからヘッダー・マップ・カードを使い、影と文字の差分を解消する。サンプルの再現が通るまで完成版全体へ展開しない。
3. 正しい字形・寸法を保った状態で共通部品化し、PC全体、SP全体へ順に展開する。
4. カルーセル末尾はPC5枠、SP7枠の計12領域を作成する。PCのゲーム・グッズは現状スクロールしないため、末尾フレームを作らない。
5. SPメニュー開、看板2・3枚目／登録者数、装飾・ホバーの代表状態を追加する。
6. 同一寸法の画像比較で最終調整し、編集可能な範囲と残る再現差を記録する。

補足: SPはscroll-snapによりscrollLeftが理論上の最大値の約15〜16px手前に落ち着くことを実測した。末尾カードは全体が見えており、矢印は非表示。補足フレームにはこの実際に落ち着いた位置を使用する。
