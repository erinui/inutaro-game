# TOPの固定マップとレコメンド配置の変更仕様

現行仕様・改修工程・受入条件は[TOP改修SDD](top-redesign-sdd.md)を参照。本書は検討・レビュー時点の記録として保持する。

2026-10-18 設計資料統合: 作成済みPC・SPのデザイン方針は[TOP新レイアウト デザイン設計書](top-redesign-design-spec.md)、確定寸法・部品・座標・検証条件は[詳細設計書](top-redesign-detail-spec.md)を参照する。本書は変更経緯と制作記録として保持する。新規実装では両設計書を本書の初期仮寸法より優先する。

作成日: 2026-10-18 / 版: 1.0 / 状態: デザイン作成・実装に向けた変更仕様

PCではマップをブラウザの表示高さに収めて左側に固定し、残りの横幅にレコメンドカルーセルを縦に並べる。マップのスポット選択は、別ページへの遷移から、対応するレコメンド枠への自動スクロールへ変更する。SPではマップをファーストビューに置き、その下に同じレコメンド枠を続ける。

本書は今回のTOP新レイアウトの変更経緯と制作記録を定める。既存の公開サイトを再現した[画面設計書](screen-design-specification.md)や[総合仕様](site-specification.md)のうち、TOPの配置・マップの遷移先に関する記述は、新レイアウトを制作する際に冒頭の新設計書を優先する。Webソースと公開サイトの実装記録は別に管理する。

## 1. 対象と確定した変更

制作対象はFigma「サイトマップ _共有」の作業ページ「TOP v2 / まち歩きガイド / 2026-10-15」内にある「PC新レイアウト検討」。既存の「TOP / PC / 1440 / 全体（編集可能テキスト）」および既存SP・v2フレームは参照元として保持する。SPは新レイアウトのレスポンシブ仕様を本書で定め、既存SPを無断で上書きしない。

| 項目 | 今回の確定方針 | 置き換える直前案 |
| --- | --- | --- |
| PC左側 | マップを固定表示。ブラウザの縦幅に合わせて地図全体を収める | 導入文・説明・主要導線を含めた大きな固定ファーストビュー |
| PC右側 | 各レコメンドカルーセルを縦に配置し、左マップ以外の横幅を使用 | 左右720pxずつの固定配分、SP相当の細い列 |
| マップの操作 | 対応するレコメンド枠へ自動スクロール | スポットから直接、下層・外部ページへ遷移 |
| コンテンツへの遷移 | レコメンド内のカード・既存CTAから遷移 | マップとレコメンドの両方を直接遷移に使用 |
| SP | マップを先頭に配置し、その下に全レコメンドを通常フローで接続 | PCの固定表示をSPでも継続 |

固定領域に導入文や説明パネルを新たに増設しない。共通ヘッダーの既存ロゴ・ナビは別の共通領域として扱い、必要な高さだけマップの利用可能高さから差し引く。マップ内の道路文字・既存の名称は保持する。

## 2. PCの寸法設計

### 2.1 高さからマップの幅を決める

左右を一定割合で分割せず、次の順序で寸法を決定する。数値はCSSピクセル。ブラウザ外枠やOSメニューバーではなく、Webページの表示領域を基準にする。

| 記号 | 定義 |
| --- | --- |
| W / H | ブラウザの表示幅 / 動的な表示高さ |
| Hheader | 共通ヘッダーが表示領域を占有する高さ。使用しない構成では0 |
| Pt / Pb | マップ領域の上下余白。枠線・影・装飾の収まりも含める |
| Pl / Pr | 固定領域の左右余白 |
| R | マップの基準幅 ÷ 基準高 |
| Hmap | `H − Hheader − Pt − Pb` |
| Wmap | `Hmap × R` |
| Wleft | `Pl + Wmap + Pr` |
| Wright | `W − Wleft`。左右の間に区切り幅を設ける場合はその分も差し引く |

既存Webの `.map-stage` は402:639。これは計算の参照値とし、Figmaで使用するマップは装飾・影まで含む実際の境界を確認してRを確定する。上下に飛び出す装飾がある場合、それを切って「全体表示」と扱わない。

寸法検討用の仮条件を `Hheader=80、Pt=Pb=Pl=Pr=24、R=402/639` とした場合:

| 表示領域 | マップ高 | マップ幅 | 左領域幅 | 右領域幅 |
| --- | ---: | ---: | ---: | ---: |
| 1440×900 | 772 | 約486 | 約534 | 約906 |
| 1366×768 | 640 | 約403 | 約451 | 約915 |
| 1280×720 | 592 | 約372 | 約420 | 約860 |

上表は計算例であり、ヘッダー80pxや余白24pxを確定寸法とするものではない。1440×900で左右720pxずつに固定したり、右側を390pxのまま残したりしない。

### 2.2 マップの表示と座標

- 地面・道路・建造物・キャラクター・操作領域を一つの基準座標系で管理する。
- 全体を同じ倍率で拡縮し、縦横比を維持する。画像はcontain相当とし、coverによる切り抜きはしない。
- PCとSPで建造物の順番、相対座標、重なり順を変更しない。画面幅に応じて建物を並べ直さない。
- 画像だけを縮小して透明なクリック領域を元の座標に残さない。表示とヒット領域は同じ変換に追従させる。
- 低いウィンドウ、ブラウザズーム、サイズ変更でも全体が表示され、マップ内に別の縦スクロールを発生させない。

### 2.3 スクロールの持ち方

縦スクロールはページ全体の一系統を基本とする。左マップを画面内に留め、右のコンテンツだけが移動して見える構成にする。右側の上にポインターを置いたときだけ動く独立スクロールや、左右それぞれのスクロールバーは原則として設けない。

Web実装では、左領域をsticky相当、右を通常の文書フローに置く方法を第一候補とする。固定を成立させる親の高さ・overflowを確認し、長い右領域の途中で左マップが追従を終了しないようにする。共通ヘッダーが固定される場合、マップの上端をその下に合わせる。フッターも右側の末尾に含める。

## 3. 右側のレコメンド設計

縦方向の順序は、現在の検討レイアウトを引き継いで次のとおりとする。

1. ニュース
2. キャラクター紹介
3. ゲーム
4. YouTube
5. ブログ
6. グッズ
7. LINEスタンプ
8. 既存フッター

各セクションは右領域の幅いっぱいを使い、内側に共通の余白とカルーセル操作領域を確保する。SPの390px画面全体を拡大縮小して貼る方式にはしない。カード・文字・余白をそれぞれ可変領域に合わせて配置する。

| 項目 | 仕様 |
| --- | --- |
| カード寸法 | 一つの表示幅では、レコメンドカードの外寸を統一する。変更後の基準寸法は右領域で実測して確定し、現行321×432pxを無条件に拡大しない |
| 枚数の見せ方 | 右領域に入る完全なカードと、次のカードの一部を表示する。複数枚ある場合に続きが分かる構成を維持する |
| 広い画面 | 余白だけを広げたりカードを無制限に巨大化したりせず、見えるカード枚数を増やす |
| 枚数が少ない場合 | 全件収まれば自然に表示し、見切れの演出のためにカードを複製しない |
| 左右矢印 | カードエリアの左右に配置。隣のセクションや画像・本文に重ならず、記号をボタンの中央に置く。先頭・末尾状態を区別する |
| サムネイル | カード内側の余白を揃え、共通の画像枠に全体表示。既存画像の内容を生成・描き足し・意図しないトリミングで変更しない |
| カテゴリラベル | 必要な混在枠ではC2を維持。画像と本文の境界、丸いカプセル、GAMEは淡黄・YOUTUBEは淡桃・NOTEは淡緑。単一カテゴリの枠に同じカテゴリ名を各カードへ重複表示しない |
| 横操作 | 矢印、タッチスワイプ、トラックパッドに対応。縦方向のページスクロールを妨げない |
| データ更新 | 画像ロード・最新データ取得で上のセクションの高さが変わり、到着先が大きくずれないよう画像枠とカード高を先に確保する |

セクション間の淡色背景と波形は右領域の横幅を基準に描く。固定マップ側へセクションの色帯を横断させない。左側は共通の背景にまとめ、スクロール中もマップの位置が安定して見えるようにする。配色の実値はユーザーが編集した最新Figmaを参照し、本書のために旧配色へ戻さない。

## 4. マップの移動先と操作

### 4.1 対応表

実装時は既存見出しIDを優先して使用する。IDは2026-10-18時点の `index.html` から確認したもの。Figmaでは同名のセクション見出しをScroll toの対象にする。

| 既存のマップ要素 | 変更後の対象レコメンド | 既存の見出しID | カードから先の遷移 |
| --- | --- | --- | --- |
| `.map-link-character` | キャラクター紹介 | `character-title` | 既存の紹介ページ・該当キャラクター |
| `.map-link-game` | ゲーム | `game-title` | ゲーム本体・ゲーム一覧 |
| `.map-link-youtube` | YouTube | `youtube-title` | 各動画・チャンネル |
| `.map-link-blog` | ブログ | `blog-title` | 各記事・note |
| `.map-link-goods` | グッズ | `goods-title` | 各商品・既存ショップ |
| `.map-link-linestamp` | LINEスタンプ | `line-stamp-title` | 各スタンプ・既存ストア |
| `.map-link-sns` | 対応枠の決定待ち | 既存の専用レコメンド枠なし | 既存XアカウントのURLは素材・データとして保持 |
| `.map-link-illustrate` | 対応枠の決定待ち | 既存の専用レコメンド枠なし | 既存イラストページのURLは素材・データとして保持 |

ニュースは右側の先頭枠として残す。既存マップにニュース専用スポットがあるとは扱わず、新しい建物を勝手に追加しない。X・イラストを別カテゴリへ便宜的に割り当てたり、対応先なしのスポットへ自動スクロールを設定したりしない。専用枠の追加、既存枠への統合などは決定後に本表へ追記する。この2項目は全スポットの動作完成を判定する前の解決事項とする。

さすけ・ぶくろちゃん等の装飾用アクションは、レコメンドへ移動するスポットと区別する。既存の反応・アニメーションを、今回のリンク変更に伴って無断で置き換えない。

### 4.2 自動スクロールの仕様

- 対応が確定しているスポットのリンク先を同一ページ内の見出しアンカーへ変更する。マップからは下層・外部ページや別タブを開かない。
- PCでは左マップの画面内位置を変えず、右側の対象セクションの見出しと先頭カードを視認できる位置へ移動する。SPでは同じ見出しへページをスクロールする。
- 固定ヘッダーがある場合、その高さと上余白を到着位置に反映する。セクション末尾などスクロール上限で完全に揃わない場合も、対象見出しが隠れないことを優先する。
- 同一ページ内のリンクとしてURLフラグメントを利用できるようにする。フラグメント付きURLの直接表示、再読込、ブラウザの戻る／進むでも同じ対象へ到達できることを確認する。
- 操作による移動には滑らかなスクロールを用い、動きを抑える設定では即時移動に切り替える。所要時間はプロトタイプ確認で調整し、長い距離を一定速度で延々と移動させない。
- 連続でスポットを選んだ場合は最後の選択を優先する。ユーザーがホイール・スワイプで操作を始めたときに自動スクロールを強制継続しない。
- 対象枠のカルーセルを勝手に先頭へ戻さない。横方向の閲覧位置は、データ更新等の必要がない限り維持する。
- マップ操作による到着時は、対象見出しへ読み上げ・キーボードの移動先を合わせる。通常の手動スクロールではフォーカスを奪わない。
- 操作名は「YouTubeのレコメンドへ移動」など、実際の動作に合わせる。色だけで操作可能性・選択状態を伝えず、見えるフォーカス表示も設ける。
- 地図縮小時も各操作領域を選択できる大きさに保つ。透明なヒット領域の拡張で隣接スポットが重複しないか確認する。

到着後の常時ハイライトや現在地のマップ連動は、基本動作を確認した後の追加検討とする。必須機能のように新しいラベル・番号・アイコンを増設しない。

## 5. SPと切替条件

SPの順序は「共通ヘッダー → マップ → ニュース以降のレコメンド → フッター」。マップは固定を解除し、先頭の通常フローに置く。SPでもマップの各スポットから下方の該当枠へ自動スクロールする。

マップは表示幅・利用可能な高さの両方を確認して全体表示する。PCと同じ地図・座標を使用し、ファーストビューを成立させるために建物を消したり、上下を切り抜いたりしない。SPの本文領域は画面幅に合わせ、カードの次が見切れるカルーセルを継続する。マップと右側コンテンツをSPで重複掲載しない。

PCへの切替は横幅だけで決めず、算出したWrightがカルーセルの必要幅を満たすかも判定する。初期検討は1024px前後を境に開始し、右側にカード1枚・次の見切れ・左右操作領域が収まることを条件に実測で確定する。高く細いウィンドウなどで残り幅が不足する場合はSPと同じ縦積み構成へ切り替える。横長で高さが低い場合も、マップの操作性を確認する。

## 6. Figmaでの作成方針

既存の「PC新レイアウト検討」を制作対象とし、最新のユーザー編集を読み取ってから作業する。現在の1440×5648pxの長いフレームは、表示領域とコンテンツ全長を区別して整理する。

| 制作物 | 構造・用途 |
| --- | --- |
| PCプロトタイプ | 1440×900pxを基準とする画面フレーム。共通ヘッダー、固定マップ、縦長のレコメンドコンテンツを含める |
| PCの固定マップ | ヘッダーを除く表示高さに収める。ページスクロールで動かない設定にし、地図とヒット領域を一緒に拡縮する |
| 右側コンテンツ | 右側の残り幅に合わせた縦Auto Layout。各セクションと横カルーセルを配置し、全長を編集できるようにする |
| 画面フレームのスクロール | 縦スクロールを一系統に設定する。固定マップは固定レイヤー、右の内容はスクロールするレイヤーとして扱う |
| 地図内の操作 | 対応する右側セクションにScroll toを設定。別ページ遷移の旧インタラクションを混在させない |
| SP検証用 | 390×844pxの表示領域を基準に、マップを先頭・レコメンドを下に接続。既存SPを上書きせず新レイアウトの検証用として分ける |

文字は既存のKeinannPOPjpによる編集可能TEXTを維持し、アウトラインへ変換しない。既存のキャラクター・マップ・サムネイル素材を使い、新規生成しない。階層は「共通ヘッダー／固定マップ／レコメンド／セクション／カルーセル／カード」を基本に、レイアウト・スクロール・編集に必要なコンテナだけを置く。カード全体やSP全長を一枚画像へ変換しない。

Figmaの固定サイズのプロトタイプで確認できる範囲と、Webでの動的なブラウザサイズ変更を区別する。1440×900pxで動いたことだけを、全PC幅・高さでの合格とはしない。

## 7. 制作と確認の順序

1. 最新の「PC新レイアウト検討」と既存SPから、素材・地図座標・カード内容・フォント・背景の編集状態を確認する。
2. マップの実境界と共通ヘッダー高を測り、基準画面で左幅・右幅を計算する。
3. 右側のセクション・カード・カルーセルを可変幅へ整理する。サムネイル余白とC2ラベルの収まりを確認する。
4. 固定マップと縦スクロールを設定し、確定済み6スポットから該当枠への移動を設定する。
5. SPで同じ地図・読み順・リンク先を接続し、幅・高さが異なる画面を検証する。
6. X・イラストの対応先を決定して操作表へ反映する。全スポットの確認後に制作結果を記録する。
7. Web実装を行う段階では、旧リンク保持の試験条件を今回承認されたマップ内アンカーへの変更に合わせて更新する。カードの外部URLや取得データ、ゲームロジックまで一括変更しない。
