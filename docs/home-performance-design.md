## 4. 資産・設定の管理方式

### 4.1 静的な不変資産

配置先は `assets/versioned/`。名前は `<用途>.<最終バイト列のSHA-256先頭16桁>.<拡張子>` とする。画像は候補採用後、フォントは分割後、CSSは参照URL書き換え後にハッシュ化する。同じ短縮ハッシュで異なる内容が出た場合は生成を失敗させ、フルハッシュで衝突を確認する。

生成済み画像・フォント・CSS・JSを公開単位に含める。ビルドは従来の追跡assetsに加え、非公開manifestに明記され、パス・完全SHA・有効source SHAを検証した生成物だけをコピーする。これによりGit indexを変更せず、未stageの改修を試験できる。任意の未追跡assetsは公開しない。公開準備ではmanifest・生成物・コードを同一変更に含め、クリーンなcheckoutからビルドする。ビルド時の依存パッケージ追加やフォント再生成はしない。実装用の生成スクリプトが最新ソースと生成済み資産を照合し、古い生成物・参照欠落があればビルドを失敗させる。

旧root CSS/JS、旧SVG/PNG、元TTFは保持する。新版HTMLは新ハッシュ資産を参照する。旧ハッシュ資産も少なくとも1年保持し、その間は自動削除しない。古いページからの要求を保証するための保持期限と、ブラウザが実際に保持する期間は別の概念である。

### 4.2 更新されるデータと画像

JSONと自動更新サムネイルは `assets/home-city/` に置き、再検証を維持する。新YouTube画像も `/assets/versioned/` には入れない。

YouTube画像の名前は `youtube-thumb-<videoId>-<contentHash16>.webp`。動画のインデックスに依存せず、最終WebPバイト列のハッシュを使う。動画IDは英数字・`_`・`-` のみを許可し、パス区切り・URL・相対パスを受け入れない。同じ動画で画像が更新された場合もURLが変わる。

新形式の画像は今回自動削除しない。古いJSON・開いたままのページ・切り戻しからの参照を守るためである。画像数と保存容量を結果レポートへ出し、整理は保持要件を確認する別作業とする。note画像は現行契約のまま今回の長期キャッシュから除外する。

### 4.3 内部manifest

新規 `config/home-performance-assets.json` を生成物の正本にする。項目は、仕様version、sourceパスとフルSHA、出力パスとフルSHA、MIME、幅/高さまたはunicode集合、変換パラメータ、生成ツール版、作成理由。CSS/JSも元ソースSHAと変換後SHAを保持する。

現在のHTMLへ適用する有効参照と、旧ページのために保持する旧出力を区別する。有効参照は対応するsource SHAと生成物を照合し、保持出力は保存時の由来・フルSHA・ファイル存在を照合する。旧出力のsource SHAが現在ソースと違うことだけでstaleにしない。切り戻し時はソース・有効参照・変換manifestを合格版へ揃え、保持出力を残す。HTML参照だけを戻してビルドで新版へ再置換される操作は行わない。

manifest・比較画像・試験記録は公開しない。既存ビルドはconfig/docs/testsを列挙していないため、その境界を維持する。秘密情報や外部APIキーを記録しない。

## 5. マップ・その他画像設計

### 5.1 対象と形状

| 素材 | 形状・注意 | 処理 |
|---|---|---|
| `map_sns2.svg` | 1000×1000 viewBox、埋め込みPNG＋パス等 | 最初の比較対象 |
| `map_character.svg` | viewBox `170 75 650 816` | 切り抜きと650:816比率を保持 |
| `map_goods.svg` / `map_linestamp.svg` / `map_game.svg` | 1000×1000、pattern・clip等 | SVG全体を描画 |
| `map_note.svg` / `map_illast.svg` / `map_youtube.svg` | 同上。YouTubeは画面・枠の重なりあり | 個別描画と組合せ表示を確認 |
| `map_bg.svg` / `map_youtube_bg.svg` | 背景と画面部品 | 原則維持。大容量なら別候補として記録 |

### 5.2 変換パイプライン

1. ローカルHTTP経由で元SVGを読み、Playwright＋固定版Chromiumの独立した透明ページで描画する。margin、背景、外部CSSを除き、SVG自体のviewBox・path・pattern・clipをすべて適用する。
2. 要求解像度どおりの透過PNGを生成する。CSSのdrop-shadow・拡大補正は元ページ側の処理なので画像には焼き込まない。
3. PNGを共通中間成果物にしてWebPの品質80・90・lossless候補を作る。圧縮ツール版と設定を記録する。抽出した埋め込みPNGや同名の旧PNGを中間成果物にしない。
4. アセット単体とページ内の両方で比較し、最小の合格候補を採用する。SVG描画器変更は別の候補比較として扱う。
5. 採用ファイルをハッシュ命名してGit管理し、manifestへ登録する。変換は通常ビルド・定期更新と分離する。

必要幅は `ceil(変形後の最大CSS描画幅 × 対象DPR)`。PC/SP・境界幅・既存scale補正を実測する。DPR1/2を主対象にし、DPR3の高密度端末でも輪郭が許容範囲か目視する。比率から高さを算出し、端数丸めによる差も記録する。必要なら1x/2x候補を `srcset` / `sizes` で選択させるが、不要な全候補preloadはしない。

`.map-image-svg` は拡大補正クラスとして引き続き使う。名前を理由に除去しない。`width` / `height` は採用画像の比率どおりとし、既存 `width:100%; height:auto` を維持する。picture導入はAVIF等が必要になった場合に限定し、既存の子要素セレクタを検査する。

### 5.3 視覚の採用条件

Chromeと利用可能なSafariで、390/1440幅、DPR1/2、通常/hover、YouTubeの動画/統計表示を比較する。レイアウトは既存の主要境界幅も確認する。画像比較時だけアニメーション時刻を固定し、性能計測では固定しない。

位置・寸法・重なり・クリック対象の意図した変化は0。輪郭欠け、文字判読性低下、色の変化、透過縁の白黒にじみ、影の二重化があれば不採用。差分ヒートマップは補助に使い、圧縮に伴う画素差の有無だけで採否を決めない。採用理由と原本対照を保存し、判断できない素材は保留する。

### 5.4 その他画像

キャラ5枚は共有ページの最大幅も含めて解像度を決定する。ゲーム紹介画像はTOPと一覧の両方で確認し、ゲーム内描画素材を変更しない。ロゴはヘッダー専用画像を追加し、PWA用192/512画像のURL・役割を維持する。apple-touch-iconの減色は見た目を維持できる場合だけ採用し、favicon保持試験の変更記録を付ける。

## 6. フォント配信設計

### 6.1 表示方式だけの変更

共通 `@font-face` の `font-display` をblockからswapへ変える。family、weight、src、preload、文字集合はこの段階では変えない。新CSSを生成し、この変更だけの差分を計測する。完成後の字形・改行が原本と一致することに加え、フォント遅延・失敗時も文言が読めること、切り替え時のCLSを確認する。

### 6.2 分割方式

元JP TTFのcmapを基準に、元の全文字集合を維持する。固定文言の集合と、その他の集合を重複なく分割する。現在のHTMLだけから残り文字を削除する方式は採らない。

固定集合はHTMLのテキスト・必要な属性、JSで描画する文言、CSSのcontent、全共有ページから抽出し、人が抽出結果を点検する。最新JSONは使用頻度・予算確認用に参照するが、データ更新ごとにフォントを再生成しない。残余集合はまず64/128コードポイント程度の候補で比較し、関連glyphとlayoutテーブルをFontToolsに保持させる。

すべて同じfont-family・style・weightを使い、各ファイルに実収録文字と一致する `unicode-range` を設定する。集合の和が元cmapを覆い、交差が空であることを試験する。範囲に1字でも該当するとその分割全体を取得するため、初期容量は実際の全取得量で評価する。全文字版を無条件fallbackのfaceとして重ねない。

採用候補は142の排他的face。TOP固定文字、欧文/結合文字、かな/半角かなの組版クラスタを同じfaceにまとめ、原本全cmapを残余faceで覆う。横書きの既定機能 `liga/kern/rtla`、アウトライン、hmtx、原本のglobal bounds、hintと名称を保持する。現行CSSにない縦書き・字幅変換・任意feature指定は分割版から除き、新規利用時はfont policyでビルドを停止して再生成・再検証する。分割集合は `config/home-font-partitions.json` に固定する。

初期はpreloadなしを基本とし、実測で効果がある固定集合だけに限定して追加できる。元のフル版preloadは分割採用時に全共有HTMLから外す。font-displayはswapを継続する。元TTF/WOFF2は旧URLで保存し、元フォントにない文字は既存のsystem fallbackで表示する。

### 6.3 検証

各コードポイントのアウトライン、advance幅、ベアリング、必要なlayout機能を元TTFと対応付けて比較する。glyph IDの再番号だけを字形差と扱わない。共通見出し、長い日本語、数字、記号、元フォント内の低頻度文字を含む将来タイトル、絵文字、結合文字をfixtureに入れる。

静的全文字・動的fixtureを表示した状態で、Chrome/Safariの改行と描画を確認する。非表示DOM・画面外の文章でも取得が起きうるため、初期viewportの文字数だけで予算を推定しない。100KB目標を満たせなければ分割幅と固定集合を再検討し、未達を明示する。ゲーム専用の元版フォントは対象外。

## 7. YouTubeデータ・画像契約

### 7.1 JSONの追加項目

既存キーと `thumbnail.url` は上流URLとして維持し、schemaVersionとlocalThumbnailを追加する。旧クライアントは従来のthumbnailを読める。新クライアントは検証済みlocalThumbnailを優先する。

```json
{
  "schemaVersion": 2,
  "ok": true,
  "videos": [{
    "id": "VIDEO_ID",
    "title": "既存の動画タイトル",
    "url": "https://www.youtube.com/watch?v=VIDEO_ID",
    "thumbnail": { "url": "https://i.ytimg.com/上流画像.jpg" },
    "localThumbnail": {
      "url": "assets/home-city/youtube-thumb-VIDEO_ID-HASH16.webp",
      "width": 640,
      "height": 360,
      "sha256": "最終WebPのSHA-256・実装時は64桁hex"
    }
  }]
}
```

これは構造例であり、そのまま検証を通るfixtureではない。実データには既存のchannel、fetchedAt等も保持する。最大6件の各動画に対し、上流画像があるものはすべてローカル変換する。上流画像なしはlocalThumbnailを省略し、既存の代替表示にする。

640×360は上限候補。縦横比を保ち、拡大せず、必要な表示幅を確認して採用寸法を決定する。画像内容を勝手に切り抜かない。APIが返した候補から必要解像度を満たす最小候補を選び、常にmaxresを選ぶ処理をやめる。WebP変換後にデコード可能性と寸法を検証する。

### 7.2 互換移行

- 第1段階: 新consumerはv1/v2両JSONを受け入れる。v1では従来画像を使い、容量改善は未達として記録する。API fallbackの旧スキーマも維持する。
- 第2段階: collectorがv2を生成する。旧 `youtube-thumb-1..5.jpg` は旧HTMLのために保持し、v2導入中も先頭5件の対応を維持する。新画像へのURL変更と無関係に既存JPGを削除しない。
- 新しい全表示箇所はv2の同じlocalThumbnail URLを使う。旧クライアントが外部URLを使い続けることは互換動作として許容し、新版の性能結果と混ぜない。
- v2でlocalThumbnailのある項目が読込失敗したら、別動画の旧JPGではなく既存の代替表示へ進む。画像のない項目だけを失敗とし、全カードを止めない。

### 7.3 収集・検証・保存

既存の取得先別stageを維持する。取得→画像変換→ローカル画像のフルハッシュ/寸法確認→JSON作成→出力集合検証の順で完了させる。変換失敗・画像破損・参照欠落はYouTube取得先全体をfailedとし、旧YouTube JSON/画像を保持する。note/SUZURIの正常分は従来どおり進める。

`validateOutput` は旧JPGに加え、新命名のWebPとJSON内の対応を許可する。拡張子・magic bytesだけでなくデコード、正の整数寸法、寸法と実体の一致、sha256一致、videoIdとの一致、ファイル集合の過不足を確認する。過去世代の保持対象は「今回生成した必須出力」と区別し、stageの無関係ファイルを許可しない。

新画像はadd-onlyで反映し、JSONの変更はその後にする。途中の書込失敗では元状態へ戻す現行の復元契約を維持する。旧ハッシュ画像を消さないよう、YouTubeの削除集合計算を変更する。publishの許可パス・SHA確認・空index・開始コミット一致・1commit/1pushを維持する。

変換はNode20から実行できる固定版cwebp等の明示した依存で行い、CIのセットアップに記載する。工程P0でローカル/CIのツール版と導入手順を固定する。変換不能時に元画像をWebP拡張子で保存するfallbackは作らない。現行の各HTTP12秒・collector180秒・job15分を維持し、その範囲で全6件を処理できることを試験する。

## 8. ビルドと初期HTMLの整合

### 8.1 初期サムネイルの二重取得を防ぐ

静的HTMLの古いローカルJPGを取得後、JSが最新動画画像へ置換する現状を改善する。ソースHTMLの対象に明示的な `data-latest-video-index` を付け、公開ビルド時に同一snapshotのYouTube JSONから画像・リンク・タイトルを対応付ける。マップ画像枠、動画カード、ニュース内の動画カードだけを対象にし、他の本文は変更しない。

新規 `scripts/lib/home-youtube-snapshot.mjs` を純粋な変換関数として用意する。DOM位置の曖昧な正規表現置換を避け、明示した属性と出現数を検査する。JSON全体の内容ハッシュを `data-youtube-snapshot` として出力する。ハッシュ一致を理由にhydrate全体を省略しない。画像URL・寸法・内容が一致する既存ノードへの再代入だけを省き、必要なカード数・順序・リンク・「もっと見る」の整合処理は必ず行う。最新情報の他ジャンル更新でも既存画像ノードを安定キーで再利用する。

書き換え対象を分ける。マップはサムネイルと統計だけを更新し、既存のチャンネルURL・アクセシブル名を維持する。動画一覧とニュース内の動画カードは、その項目の動画URL・タイトル・画像をひと組で更新する。静的動画一覧は既存3枠を上限に、有効動画N件なら先頭min(3,N)件を生成する。N=0は動画IDを持たない汎用チャンネル案内を既存の代替表示として残す。存在しないインデックスに別動画を繰り返して入れない。

JS有効時は同一snapshotでも、N>0なら動画IDを安定キーに先頭min(5,N)件へ必ず整合させる。N>5のときだけ「もっと見る」を1件置き、N<=5では除去する。既存動画ノードを移動/再利用し、不足分だけ追加、余剰分だけ除去する。N=0は汎用チャンネル案内とし、古い動画カードを最新動画として残さない。JS無効またはJSON取得失敗はビルド済みsnapshotを維持する。

HP-T07では同一snapshotのN=1/3/5/6を必須化する。N=6なら静的3件から既存3画像を保持したまま5件＋「もっと見る」へ、N=5なら5件のみへ整合する。2回目の同一hydrateでノード追加・画像src再設定が発生しないことも確認する。件数減少・並べ替え・N=0は異なるsnapshotでも検査する。

ビルド中の変更を避けるため、コピー済み出力のJSON/画像からsnapshotを作る。ソースのJSON/画像SHAが処理中に変わった場合は出力を失敗扱いにする。v2で存在する画像の参照欠落はビルドエラー。v1は互換出力として許可するが、v2導入後の本番性能の合格対象にしない。

JS無効時もビルド済み最新カードが表示される。JSON取得失敗時はsnapshotを保持する。snapshotに項目がないときは既存の代替カード・画像を使い、削除済み動画へ別動画の画像を割り当てない。JSONの動画内容と連動するラベル変更だけを許容し、原稿編集と混同しない。

ソースをそのまま配る簡易プレビューは最終検証に使わず、生成済み出力を配るHTTPモードをテストhelper/previewに追加する。旧GitHub Pagesのサブパス、拡張子なし本番URL、通常の相対リンクを壊さない。

### 8.2 CSS/JSのハッシュ参照

`home.css`、`home.js`、`site-nav.js`、`site-migration.js` の新版を資産manifestからHTMLへ適用する。CSSのurl()は新配置から参照できる相対URLへ変換し、ページごとに異なる絶対root依存を作らない。JSの文書基準相対URLは、スクリプトURL基準に変わったと誤解して書き換えない。

処理順は画像/フォント生成→CSS内URL確定→CSSハッシュ→JSハッシュ→HTML参照更新。生成物に手編集を加えず、同じソースとツール版から同じ出力を再現する。生成スクリプトは削除やstage/pushを自動実行しない。

ビルド出力には従来公開ファイル、追跡済みassets、manifestで完全SHAを検証した生成物、JSONが参照し完全SHAと寸法が一致するローカルYouTube画像、新版生成HTMLだけを含める。公開ファイル一覧試験は許可した変換分だけ更新し、docs/config/tests/drafts/env/functions/3D試作を含めない。新規出力ディレクトリ必須の契約を維持する。

## 9. 読み込みとスライド状態管理

初期LCP要素はPC/SPごとに計測する。初期表示に必要な画像はeager、優先指定は測定した候補に限定する。CSS背景や文字LCPなら、無関係なimgをhighにしない。画面外画像はlazy/asyncとし、JS生成カードも枠比率を確保する。

YouTubeの非表示画像は `src` の代わりに `data-src` を保持する。スライドごとに idle/loading/ready/error、動画ID、URL、世代tokenを管理する。次スライドは表示予定の2秒前を初期値として取得・decodeを開始し、通信状況に応じた調整は計測で判断する。

10秒ごとの表示更新でreadyなら切り替える。未完了なら前の画像を維持し、完了時に予定表示がまだ同じ場合だけ切り替える。errorなら既存代替表示にする。統計パネルは画像取得なしで表示する。古いJSON世代のdecode完了が新世代を上書きしないようtokenで破棄する。無制限な自動リトライは追加しない。

`youtubePanel` / `showStats` は初期表示の指定として維持し、指定動画は直ちに準備する。`youtubePanel` を使う視覚試験と、通常の10秒切り替えを使う性能試験を分ける。

## 10. キャッシュ・公開・切り戻し

既存2つのnoindexルールに次だけを追加する。広域のCache-Controlと個別例外の上書き順に依存しない。同名ヘッダーの重複適用は値が結合される仕様のため、競合を検査する。

```text
/assets/versioned/*
  Cache-Control: public, max-age=31536000, immutable
```

HTML、最新JSON、同名更新画像、新YouTube画像は現行の再検証を維持する。新YouTube画像の名前は内容識別のためにハッシュ化するが、今回長期キャッシュには含めない。

公開は新旧資産を含むひとつの静的releaseとして行い、新HTMLだけ先に配る工程を作らない。プレビューでHTML/JSON/画像/フォント/旧URL/noindexを確認後、公開用コミットを確定し、そのSHAとビルドIDを記録する。

### 10.1 資産を保持する復旧release

標準の切り戻しは、**直前合格版のコード＋最新の正常データ＋保持対象資産の和集合**を新しい復旧releaseとして再公開するforward rollbackとする。直前合格版のソース・HTML参照・有効manifest・ビルド変換を揃え、最新の保持画像/フォント/CSS/JSを追跡assetsに残して新規出力先へビルドする。新データは旧consumerでも読める契約にしておく。

復旧前に保持対象URL一覧とフルSHAを照合する。対象は現行/直前合格HTML・公開中のJSON・開いたままの旧新版ページから遅延要求される、保持期間内の全ハッシュ資産と新旧画像。新しいconsumerを戻しても、そのconsumerを既に読み込んだページが要求する資産は削除しない。manifestのstale検査とsnapshot変換にも合格する復旧artifactを公開単位ごとに準備し、P7と各公開前に検証する。

Cloudflareの過去releaseへ直接戻すのは、**復帰先にこの保持対象URL集合がすべて存在し、内容が一致することを復帰前に検証できる場合だけ**許可する。新releaseで初めて追加したハッシュ資産を含まない過去releaseは対象外。資産集合またはJSON/consumer互換性を確認できなければ、緊急時も復旧releaseを再公開する。旧版へ戻してから欠落を確認する手順にはしない。

HP-T10では、新版ページを開いて遅延画像/フォント取得を保留→復旧release公開→保留を解除し、すべての要求が200かつ期待SHAで表示されることを確認する。復旧後の新規ページ・旧ページ・JSON更新も検証する。資産不足の過去releaseが復帰前チェックで拒否されることも確認する。

### 10.2 immutable誤適用時の復旧

誤った不変資産は同じURLを上書きせず、新ハッシュを作ってHTML参照を更新する。更新JSON/画像へ長期キャッシュを誤適用した場合は、設定を外すだけでは既にfreshとして保存された応答を修復できないため、取得URLも変更する。

復旧JSONのパスは元パスのbasenameに復旧IDを加えたものとする（例: `assets/home-city/youtube-latest.recovery-20261017-01.json`）。同一内容の固定コピーを作るだけにはせず、通常のcanonical JSONと同じ最新内容を以後の更新でもこの復旧URLへ出力する。復旧画像も誤キャッシュされたURLを使わず、必要なら復旧IDを付けた新URLを使う。旧URLは保持する。

実装時に非公開の `config/home-data-recovery.json` で復旧alias一覧と有効JSON URLを管理する（通常時はaliasなし）。復旧時はconsumer resolverがactive aliasを取得する。snapshotはコピー済みcanonical JSONと一致する原子生成aliasを参照する。同じ内容を入力にするため、ビルドはcanonical JSONの開始時・コピー後・終了時SHAを照合する。collectorのstage許可パスは広げず、aliasはソースツリーに複製しない。復旧URLは `/assets/versioned/` の外で、再検証ヘッダーが実際に返ることを確認する。aliasは各ビルドで、部分失敗/復元済みのcanonical JSONから全世代分を自動再生成する。データ更新だけの公開でも必ず通常ビルドを経由し、手作業コピーのまま運用しない。旧URLがimmutableのfresh期間中は復旧URLから元URLへ戻さない。

HTMLが再検証可能な場合、次の通常遷移から新HTML→新ハッシュconsumer→復旧JSON URLへ移行できる。既に開いた旧ページのresolverは書き換えられないため、自動復旧を保証しない。再遷移での復旧と、既存snapshotで表示を継続できる範囲を記録する。HTML自体もfreshとして誤キャッシュされている場合は同じURLの通常再遷移で直るとは扱わず、新しい文書URLから復旧版を取得する経路を用意し、旧文書URLの復旧未確認を明記する。ブラウザ全体のキャッシュ消去を標準手順にしない。

現行の `fetchStaticData` は `cache: "no-cache"` を指定するため、その取得経路は明示的な再検証を維持する。immutableの誤適用だけで現行の全JSON取得が停止すると仮定しない。HP-T10は、defaultキャッシュの旧/他クライアントでJSONを1年freshとして保存→サーバー側ヘッダーだけ修正しても新要求が出ないことを再現→新consumerと復旧URLへ移行→次回更新も取得、という経路を検査する。no-cacheの現行経路で再検証が成功するケース、旧ページが自動更新されないケース、HTMLも誤キャッシュされたケースは分けて記録する。

旧ハッシュ保持は通常更新だけでなく切り戻しreleaseにも必要。キャッシュ消去をブラウザ修復の前提にしない。公開・切り戻しの実行は本書作成の範囲には含めない。

## 11. 計測と試験設計

### 11.1 既存計測の修正点

`scripts/check-seo-performance.mjs` の現状は、DPR1のみ、`?youtubePanel=0` による切り替え固定、Resource Timingの同一origin合計、layout-shiftの単純加算。今回の判定へそのまま流用しない。

新規 `scripts/check-home-performance.mjs` を作り、旧スクリプトと過去の結果を残す。計測本体と視覚撮影を別contextにし、性能計測でanimationを止めない。CLSは直近入力を除外した最大セッションウィンドウ（shift間隔1秒未満、最大5秒）で計算し、元のshiftログも保存する。

文書レスポンスも含めてCDP Networkのrequest/response/dataReceived/loadingFinished、キャッシュ由来、URL、Initiator、MIME、応答コード、圧縮後本文量を記録する。イベントの種類ごとにencodedDataLengthの意味が異なるため、Resource Timingの0値やloadingFinishedの総量をそのまま本文量と呼ばない。小さな既知の圧縮応答・リダイレクト・キャッシュ応答で集計実装を校正し、本文量とヘッダー込み実転送量の取得根拠を区別する。外部通信を含む集計ができなければ容量判定は未確認にする。

### 11.2 固定条件と証跡

390×844 / 1440×900、DPR1/2、下り6Mbps・上り1.5Mbps・遅延150ms・CPU4倍、同じChrome版、各3回以上。初期計測は通常URLで操作なし30秒。全スクロール試験と視覚比較は別context。端数差の疑いがある場合は同じ条件で前後各5回に増やし、都合のよい測定だけを採用しない。

決定的な比較には同じJSON・外部応答のfixtureを使い、本番確認は実データで別に行う。圧縮なしローカルの容量と、本番Brotliの容量を直接比較しない。キャッシュ判定はWorkersプレビュー/本番と通常再訪のブラウザ試験で行う。

証跡出力先は非公開の新規ディレクトリ。保存項目: source SHA、データSHA、browser/tool版、条件、全run、中央値、外部通信の不明項目、未完了通信、LCP要素、shiftログ、HAR/CDPログ、通常/hover/各パネル画像、採否理由、公開後GETヘッダー。実ユーザーCWVはPC/SP別75パーセンタイルとしてラボから分離する。
